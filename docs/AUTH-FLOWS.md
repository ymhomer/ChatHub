# ChatHub authentication and account linking

## User flow

| Starting point | Action | Result |
| --- | --- | --- |
| Signed out, no Email login | Register Email + password, save Recovery Codes | One new account and initial space, created atomically |
| ChatGPT account, no Email login | Add Email → enter address → new address → enter new password twice | Email credential joins the existing account; no second account |
| Email account, ChatGPT identity unused | Add ChatGPT → native top-level sign-in → return → confirm | Native ChatGPT identity joins the Email account |
| ChatGPT account + independently registered Email account | Add Email → existing address → verify its original password → review data → explicitly confirm | ChatGPT account is merged into the Email account |
| Email account + ChatGPT identity that already owns another space | Start native ChatGPT link → confirm callback → verify Email password → review data → confirm | Same merge policy, independent of sign-in order |
| Email password forgotten | Recovery Code + Email + new password (twice in UI) | Password changes; all old codes and sessions revoked atomically |

Email lookup starts with an empty address field. Provider contact email is never treated as a password credential or an automatic account link. No passwords are obtained from ChatGPT.

## Merge policy

The Email account is the surviving account. Both users must be active ordinary member accounts. The ChatGPT account must not have another Email identity or Email credential. The Email account must not already have another ChatGPT identity. Unsupported/conflicting/privileged cases fail without moving data.

- Both sides must be authenticated: one current account session and the other account's Email password or native ChatGPT proof.
- Native linking starts with an HttpOnly, same-site, short-lived, single-use intent tied to the initiating account. Returning from native sign-in never mutates accounts automatically.
- A 5-minute, account-bound merge token is issued only after proof of both accounts. The user then checks an explicit confirmation checkbox and submits.
- One atomic D1 transaction checks identities, current Email credential hash, account status and replay guard before moving any data.
- Conversation memberships are deduplicated; existing admin membership is preserved. Conversations, messages, attachment references, passkeys and notification subscriptions are retained.
- Email password and its Recovery Codes remain valid. Old sessions on both accounts are revoked and a fresh session is issued.
- The old user becomes a merged tombstone. No R2 object is moved or deleted. There is no self-service split/undo after confirmation.
- Cancel, timeout, stale password/identity, replay and mid-transaction database errors do not partially move data.

## Verification

Run `npm run test:auth`.

- 15 integration tests run the production authentication functions and Drizzle against real SQLite, simulating only the request identity/cookie boundary. They cover both orders, both merge directions, wrong passwords, cancellation/expiry, unrelated sessions, replay, concurrent requests, mid-batch failure rollback, registration rollback, recovery-code rotation and recovery races.
- An additional Miniflare integration test runs the production functions in actual Workers WebCrypto and D1. It exercises new binding, both orders, both merge directions and recovery.
- ESLint and production build pass. Type checking passes with runtime declarations generated by `wrangler types` for the deployed Worker bindings.
- The account address-first UI was inspected in the local browser using a temporary fixture; the fixture was removed before packaging. `account-email-step.jpg` records that check with synthetic data.

## Remaining verification boundary

Native ChatGPT provider authorization is represented by synthetic identity headers in tests; a real user's native authorization redirect and device passkey prompt cannot be exercised by these automated tests. No real user accounts were merged during verification.

Email delivery is not configured. New Email credentials are not mailbox-verified; the UI states this explicitly. This feature does not send verification or recovery emails. Recovery uses the saved one-use codes.

## Production runtime compatibility

Production Sites rejected PBKDF2 requests over 100,000 iterations, while the newer local Miniflare runtime accepted 600,000. The password KDF is configured to the supported 100,000 iterations, with a random 16-byte salt and a 256-bit derived key. A regression test imposes the production cap during actual registration and password verification. The rate-limited `/api/auth/runtime-check` endpoint verifies hashing and verification with fixed synthetic input without creating accounts or returning hashes.
